# Data model and backup format

The authoritative TypeScript contracts are in `src/domain/types.ts`. The in-memory and exported root is `AppData` with `schemaVersion: 1`; phone-local persistence uses a compressed representation of it. IDs are stable UUIDs for user-created records and stable source IDs for built-in exercises/templates. Seed data supplies editable content and example inventories, with no fabricated sessions or personal statistics.

## Storage envelope

```ts
// localStorage key: forma.data.v1
{
  format: 'forma-local-v1',
  catalog: string, // identifier derived from bundled exercise content
  revision: number,
  writerId: string,
  encoding: 'lz-string-utf16',
  payload: string // compressed compact data; not the JSON backup format
}
```

The compact payload contains all non-catalog state plus ordered exercise IDs and full overrides for edited/custom exercises. Unchanged built-ins rehydrate from the matching bundled catalog. Removed exercises and catalog order are preserved. Historical exercise/prescription/food snapshots remain in the payload. Compression saves space and is not encryption.

`encodePersistedData` / `decodePersistedData` in `src/state/persistence.ts` encode and reconstruct this representation; initialization additionally runs `validateBackup`. Saves replace one local-storage key through a serialized queue. Exact-record checks and revision/writer metadata protect against stale writes, with Web Locks where available and a synchronous fallback with weaker cross-process guarantees. These markers are separate from `AppData.updatedAt` and schema version. See [ARCHITECTURE.md](ARCHITECTURE.md).

Records are nested rather than independent SQL-style tables. Workout sets, prescription snapshots, food snapshots and goal-history values are embedded in their parent entities. Achievements, records, streaks and most analytics are calculated from saved records rather than stored counters that can drift.

## Measurements and dates

External resistance and bodyweight are stored as kg; height as cm; distance as km; duration/rest as seconds; food amounts as grams or portion multipliers; nutrients as kcal/grams. Profile units choose kg/cm or lb/feet-and-inches entry in onboarding and Settings. Height converts with `1 inch = 2.54 cm`; display rounding and switching units do not rewrite the saved measurement. Optional blank height is omitted, and zero inches is valid when feet supply a positive height. Machine-stack/per-hand/assistance/added-bodyweight conventions are explicit and never silently treated as total barbell load.

Goal values and timeline rates use the goal's explicit unit rather than the profile display unit. Switching a supported weight goal between kg/lb converts start/current/target, recorded values, baseline and rate together. Editing an estimate baseline does not save a body measurement or append a goal-history observation. Estimated deadlines are recalculated from the saved assumptions; manually chosen deadlines stay fixed. The first reached date is derived from the earliest recorded goal-history value crossing the current target in its intended direction; there is no fabricated achievement timestamp.

Calendar fields use local `YYYY-MM-DD`; weekdays use JavaScript's `0 = Sunday` through `6 = Saturday`. Session/set timestamps are ISO instants. Calendar-week analytics start on Monday. Rest deadlines are epoch milliseconds and therefore survive navigation/backgrounding more accurately than decrement-only counters. Optional pause state stores remaining seconds. Device timezone changes affect future local-calendar grouping; the app has no separate historical timezone field.

For food records, nutrient values describe the stored `servingGrams` reference portion. A diary quantity of 2.5 multiplies all values by 2.5. A recipe sums ingredient nutrients then divides by its yield. Logged diary snapshots stay unchanged when the food collection or recipe changes. Saved diary meals freeze the actually logged foods as ingredient snapshots in the local collection.

## Snapshot and archive rules

Template edits affect future sessions. Completed and active sessions retain their copied exercise descriptions, equipment/measurement conventions and planned targets. A substitute has its own exercise ID/history, with `originalExerciseId` retained when applicable. Archive flags hide current content without deleting historical snapshots. Removing an environment preserves the historical equipment ID rather than cascading into sessions. A food cannot be removed while a recipe still references it; existing diary food snapshots remain usable when a collection food is removed.

Applying a program creates real planned calendar entries. Phase/lighter-week targets are copied into separate editable templates at application time; the base workout is unchanged. `planningSource` allows reuse of a matching generated variant and records its origin. Later program edits do not silently recalculate an existing variant. Reapplication can keep existing entries or replace unstarted plans in the block range; explicit rest days and recorded/skipped/session-linked choices are preserved. Neither operation creates completed sessions.

## Backup, restore and validation

Settings → **Backup & data** downloads a full JSON `AppData` backup, workout CSV or nutrition CSV. JSON includes active workouts, source attribution, notes, custom media, settings and all local histories. Spotify configuration/credentials are stored outside `AppData` and excluded. AI endpoint/consents are included; provider secrets are not accepted. CSV is an analysis export, not a full restore format.

Restore accepts schema version 1 only, validates before replacing local records, and changes app state only after the encoded replacement saves successfully. Validation covers types, finite/nonnegative measurements, whole repetitions, valid calendar dates/timestamps/times, supported enums, required fields, duplicate top-level/session-exercise/set IDs, selected environment, template/program/schedule references, recipe ingredients, snapshot ID agreement and rep ranges. Optional phase ranges/multipliers, goal timeline assumptions and appearance choices are validated too. A stale focused-exercise reference is cleared as disposable UI state. Invalid imports do not replace the current data. Restoring requires typed `RESTORE` confirmation; deletion requires `DELETE`.

The file-picker UI caps backup files at 20 MB; the parser separately caps pasted JSON at 30,000,000 characters. Custom exercise media has an 8 MB upload limit and expands when encoded into a data URL. Device/browser local-storage quotas may be much smaller than accepted backup/upload limits, so an accepted file is not guaranteed to save. Growing histories and media can exhaust storage. Failed saves expose an error, retain the previous saved string and leave unsaved state exportable; no records are silently discarded to make room. Keep media small and verify backups separately. Normal JSON exports are neither compressed nor encrypted.

An invalid stored record blocks further writes and remains exportable through recovery. If decompression/format/catalog matching fails, the recovery file contains `storageKey` and the exact raw saved string; this diagnostic wrapper needs repair/migration and is not a normal importable `AppData` backup. There is no automatic cloud backup, account recovery or device synchronization. Website/browser storage deletion can remove records independently of application controls. A different origin, port, browser or installed app context may have separate storage; full JSON export/import is the supported transfer path.

## Version evolution

The storage encoding and backup schema begin at version 1. The 1.2.0 application refinement adds optional appearance, phase/provenance and goal-timeline fields without changing that backup schema. Compatible older version-1 records may omit them; the appearance UI defaults to Steel blue/Comfortable and no phase or timeline history is invented.

The bundled catalog has a content-derived identifier. Supporting a new encoding/schema/catalog requires deliberate migration code and tests or a documented full-backup import path. A mismatched catalog blocks editing instead of silently replacing built-in descriptions. This repository does not claim future-version migrations. `updatedAt` is an aggregate timestamp; not every nested entity has separate creation/modification timestamps.

An implemented compatibility path reads the former `forma-training` IndexedDB `records/app` data only when the new local-storage key is missing. Native read-only access validates the full old `AppData` before saving it locally. It does not alter or remove the old record or create a new database. Current local-storage data takes precedence. Explicit full-data deletion resets current local records and deletes the legacy database; a blocked legacy deletion reports the partial result and asks the user to close other tabs.
